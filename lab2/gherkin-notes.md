# Gherkin-сценарії для обліку постачань

Основний файл: `supply.feature`. Текст кроків український; ключові слова англійські (`Given`, `When`, `Then` тощо), мова Gherkin явно задана як `en`. Сценарії є критеріями прийняття; для автоматичного виконання потрібні реалізації кроків.

## Покриття джерел

| Джерело | Покриття |
|---|---|
| spec.md | Створення, перевірка всіх позицій, порядок збереження і сповіщення, повне приймання, оновлення й створення запасів, унікальність продукт + локація, завершення, відмова сповіщень |
| EARS.md | Авторизація, ролі, локації, призначення відповідального, перегляд, помилки, повторне сповіщення після відновлення сервісу, локальне збереження даних |
| user-stories.md | Створення постачання, сповіщення, приймання, перегляд залишків |
| diagram.md | Зв'язки постачання з постачальником, локацією, відповідальним і позиціями; зв'язки позиції з продуктом і запасу з продуктом та локацією |

Теги `@spec`, `@ears`, `@story_*` позначають джерела сценаріїв. Назви сутностей у кроках відповідають ER-моделі. Операції з категоріями та довідниками не додані: для них немає відповідних історій або поведінкових вимог.

## Трактування та питання для уточнення

1. **Касир.** EARS прямо дозволяє всім авторизованим ролям приймання своєї локації, включно з касиром, але spec.md не включає касира до акторів приймання. Перегляд залишків касиром включено за EARS; приймання касиром потребує узгодження, тому для нього немає остаточного сценарію.
2. **Перегляд постачань.** Для робітника складу використано одночасно призначення йому та його локацію. Чи менеджер бачить усі постачання своєї локації, чи лише призначені йому, не визначено однозначно. Сценарій перегляду для менеджера не закріплює жодного з варіантів.
3. **Завершення.** Використано бізнес-результат «постачання завершене». У ER-моделі є тільки `чи_активний`; відповідність завершення значенню `false` слід визначити перед реалізацією кроків.
4. **Унікальність запасу.** Складений унікальний ключ продукт + локація в diagram.md явно не зазначено. Сценарії спираються на пряму вимогу spec.md про його унікальність.
5. **Валідація кожної позиції.** Застосовано вимогу коректності всіх позицій із EARS та пункту 2 логіки spec.md. Наявність однієї правильної позиції не дозволяє зберегти інші некоректні.
6. **Офлайн-режим.** Вимоги визначають збереження даних до відновлення зв'язку, але не визначають автоматичне відправлення, строки зберігання, переживання перезапуску клієнта чи вирішення конфліктів. Ці механізми не додані як затверджені критерії.
7. **Відсутнє постачання зі сповіщення.** Перевіряється результат — повідомлення адміністратора. Спосіб, у який сервіс сповіщень дізнається про відсутність постачання, потребує визначення в реалізації.
8. **Межі деталізації.** Не задані правила часткового та повторного приймання, поведінка при збоях оновлення запасів, дробові кількості, відповідність локації відповідального локації постачання та заборона неактивних локацій. Їх не додано як підтверджені вимоги. Також не встановлено строки повторних сповіщень і точні тексти помилок.

Сценарії не виконувалися проти застосунку: надані джерела містять вимоги й модель даних, а не реалізацію або тестовий стенд.
