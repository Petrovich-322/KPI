# Примітки до нового набору Gherkin-сценаріїв

Набір складено заново з поточних версій чотирьох джерел, без використання попередніх сценаріїв. Основний файл — `gherkin-new.feature`. Ключові слова Gherkin англійські, текст сценаріїв український, діалект задано директивою `# language: en`.

## Відповідність джерелам

| Теги | Джерело та покриття |
|---|---|
| @US1 | user-stories.md: створення постачання |
| @US2 | user-stories.md: сповіщення відповідального |
| @US3 | user-stories.md: повне приймання |
| @US4 | user-stories.md: перегляд залишків |
| @SPEC | spec.md: реквізити, позиції, валідація, порядок збереження й сповіщення, оновлення залишків і завершення |
| @EARS | EARS.md: авторизація, роль, локація, призначення, недоступність сервісів і локальне збереження |
| @ER | diagram.md: зв'язки сутностей, зовнішні ключі та можливість відсутності локації користувача |

## Трактування вимог

- «Замовлення» в EARS трактується як «постачання», відповідно до предметної області інших джерел.
- Для приймання обмеження за локацією застосоване і до адміністратора: виняток для нього поточні вимоги не встановлюють. Касир не включений до ролей поточного EARS.
- Перелік пов'язаних із працівником постачань фільтрується одночасно за відповідальним і локацією, як зазначено в EARS. Це не визначає, чи може існувати окремий розширений перегляд для менеджера або адміністратора.
- Для робітника складу призначення йому постачання є обов'язковою умовою приймання. Для менеджера та адміністратора позитивні приклади використовують призначені їм постачання; право приймання чужого постачання своєї локації окремо не уточнене і не закріплене сценарієм заборони.
- Усі позиції мають бути коректними: одна правильна позиція не компенсує помилки в інших. Це випливає з пункту 2 логіки spec.md та перевірки всіх продуктів у EARS.
- Тексти пояснень у таблиці валідації передають зміст помилки, а не обов'язкові дослівні повідомлення інтерфейсу.
- «Постачання завершене» — бізнес-результат. Джерела не встановлюють однозначно, чи це означає `чи_активний = false` в ER-моделі.
- Унікальність пари «продукт + локація» взята зі spec.md; складений унікальний ключ у diagram.md явно не позначено.
- ER-модель дозволяє користувача без локації. Заборона приймання для адміністратора без локації випливає з умови його прив'язки до локації в EARS.

## Межі вимог

Не визначені повторне або часткове приймання, паралельні операції, відкат при збоях оновлення залишків, точність цін, строки повторних сповіщень, автоматична синхронізація після офлайн-режиму, відповідність локації відповідального локації постачання та обмеження для неактивних локацій. Окремі правила для них не додано.

Операції керування категоріями, продуктами та постачальниками не включено: сама наявність сутностей у діаграмі не задає сценаріїв їх редагування.

Сценарії підготовлені як критерії прийняття. Для автоматичного виконання потрібні реалізації кроків і тестовий застосунок; виконання проти системи не проводилося.
